# E5：实测结论与解释边界

同一E1 adapter的BF16 batch1合并后，输出吞吐18.44→34.30 token/s（1.86倍），平均完成延迟1742.46→937.61ms。固定32条首轮EX均18/32，原始输出改变2条、改对/改错均0；三轮共96次请求用于计时。不能据小集合证明全量质量无损，也不是vLLM部署。

底座BF16 batch1→2：吞吐32.40→48.60 token/s（1.50倍），但平均完成延迟1283.93→1703.95ms。FP16 batch1→2为32.29→52.15 token/s（1.615倍）。BF16→FP16在batch1时没有观察到提速（0.997倍）。这些是不同条件实际生成输出的速度，不是固定token轨迹的算子微基准。

四个底座条件EX都为14/32，并不意味着输出相同或数值变化无风险：BF16 batch1的可执行率24/32，其余为23/32。错误SQL即使从可执行错答案变成执行失败，EX仍计错，EX总分看不出这种退化。

合并对照的两个输出变化：dev:487是MATCHES大小写与空格变化；dev:420从T2.Level_of_membership变为T2.level。后者两种写法都未通过EX，不能将“没有改错”理解为每条结构和引用都一样。原始预测保留，未手动修复后再计分。
