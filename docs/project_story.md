# 项目故事线

问题是如何让小参数模型把自然语言转换成跨数据库SQLite查询，同时在约8GB显存中完成可解释的后训练。模型固定Qwen2.5-Coder-1.5B-Instruct，不靠换大模型获得不可归因的提升。

先把数据和评测做可信：审计166个库，训练7000条/140库与dev1034条/20库不重叠，完整schema保留名称、类型和键关系。模型只看问题与schema；dev Gold留在离线评测。固定原始单库EX比较，明确不等于TSA或语义等价证明。

E0的525/1034（50.77%）EX与70.50%可执行率建立了真实起点。E1采用标准LoRA，SQL/EOS-only监督、监督位置logits、梯度检查点与累积，在本机完成7000条/438步，约49.02分钟，allocated4.516GB/reserved7.539GB。E1 EX提升到715/1034（69.15%），但仍有319条失败，248条改对的同时58条改错，不能只看平均数。

E2看到schema选择与JOIN问题仍突出，hard/extra错误率较高。由此提出一个简单代理假设：提高结构复杂训练样本的loss贡献。E3只把hard/extra原始权重设2、其他1并全局归一化，样本/顺序/token/438步不变。

E3得到726/1034（70.21%），净增11条；困难合并EX55.00%→56.18%。但可执行率88.97%→88.01%，区间包含0，schema无效引用还增加。真实案例表明部分hard收益只是值大小写或列语义改善，并不直接证明复杂结构推理增强。结论是一次探索性小幅收益，稳定性和机制没有被充分验证；保留负向指标，而不是再用dev反复搜索好看的权重。

资源效率是另一项独立问题：E4完整QLoRA已完成，训练allocated下降28.86%，耗时增加26.84%，EX68.96%相对E1的69.15%净少正确2条。同一E1 adapter的BF16 batch1合并后，输出吞吐18.44→34.30 token/s（1.86倍），平均完成延迟1742.46→937.61ms。固定32条首轮EX均18/32，原始输出改变2条、改对/改错均0；三轮共96次请求用于计时。不能据小集合证明全量质量无损，也不是vLLM部署。没有vLLM服务部署，不能写成已完成成果。

可讲述的个人项目工作是：监督和数据边界、版本锁定、安全评分、GPU内存实现、真实恢复验证、基于错误的对照设计与诚实解释。LoRA/QLoRA及官方比较器不是原创。单seed、dev用于选方法、单库EX、未知预训练数据污染和硬件测量波动都需要主动说明。
